## ADR-007 – Authentication architecture (TB-001)
- **Date:** 2026-11-04
- **Status:** **[FACT]** Decided by the project owner. Independent architect and security review completed 2026-11-04 (see Review outcome); its recommendations await owner approval. No implementation has started.
- **Context [FACT]:** Next.js frontend and Spring Boot API are separate processes; modular monolith on PostgreSQL; single developer; no Redis; web only in the MVP; users may belong to several companies with per-company roles (`company_members`); tenant isolation is mandatory on every backend query. The earlier audit found no Spring Security, open endpoints, CORS only on actuator.
- **Decision [FACT, owner-approved]:**
  1. Authentication: **server-side session** backed by PostgreSQL (Spring Security + Spring Session JDBC). JWT-based authentication is **not** used in the MVP.
  2. Production deployment: **single origin**. A reverse proxy routes `/api/*` to the Spring Boot backend.
  3. TMS/ERP machine clients: **out of MVP pilot scope**; later supported with a separate API authentication mechanism (separate security filter chain), not by weakening the session design.
  4. `PLATFORM_ADMIN`: **MFA (TOTP) and e-mail verification are mandatory before the pilot.**
  5. Session lifetime: **30 minutes idle timeout and 12 hours absolute timeout.** The absolute timeout must be implemented explicitly and covered by a test.
  6. Multi-company: in the MVP a user may be a member of several companies and **switch the active company**. Membership and role are verified by the backend on every request.
- **Additional security requirements [FACT, owner-approved]:** Argon2id password hashing · CSRF protection · strict CORS allowlist · session-fixation protection · audit logging of login, company switch, and role change · negative security tests for tenant isolation · access is cut off immediately when a company membership is deactivated.
- **Consequences:**
  - `refresh_tokens` (technical spec entity) is **not needed**; Spring Session tables replace it. Schema is created by a Flyway migration, with Spring Session auto-initialisation disabled.
  - Each authenticated request reads the session from PostgreSQL (**[ASSUMPTION]** negligible at MVP load; no cache until measured).
  - Cookie/CSRF/proxy configuration and SSR cookie forwarding must be designed and tested.
  - Backlog impact: TB-002, TB-003, TB-004, TB-005 remain blocked until the review below is recorded and any required changes are accepted.
- **Points assigned to independent review [FACT]:** Spring Session JDBC behaviour; CSRF with an SPA/Next.js; how the 12-hour absolute timeout is enforced (**[ASSUMPTION]** Spring Session's built-in expiry is idle-based, so absolute expiry likely needs custom code; reviewers must confirm); SSR cookie forwarding; tenant isolation and immediate membership revocation; TOTP/e-mail-verification flow for `PLATFORM_ADMIN`.
- **Review outcome (2026-11-04):** Two independent read-only reviews were run (Lead Architect, Security Engineer; general-purpose stand-ins using the role files). Both: **approve with changes**; neither found a flaw in the chosen approach. Library behaviour they could not verify is marked *unverified* and must be proven by tests during TB-002. The items below are **[RECOMMENDATION]**s, not yet owner-approved.
  - *Absolute 12 h timeout:* Spring Session expiry is idle-based **[unverified]**, so a request filter must enforce it from a server-side timestamp, with an injectable `Clock`. Tests: 11h59 valid, 12h01 denied despite constant activity, 31 min idle denied, 29 min idle valid, client cookie tampering irrelevant. Session rotation (login, company switch, step-up) must **not** reset the absolute deadline. Cleanup cron is never the enforcement point. Session cookie without Max-Age.
  - *Spring Session JDBC:* add `spring-boot-starter-security`, `spring-session-jdbc`, Bouncy Castle (Argon2). Copy DDL from the library's `schema-postgresql.sql` for the BOM-resolved version into a Flyway migration; `initialize-schema=never`. Store only primitives in the session (user id, active company id, authentication time), never entities or role. Use the principal-name index to delete all of a user's sessions. The no-DB context test needs session store type `none`.
  - *CSRF (SPA + SSR):* cookie-based token with Spring's SPA handler pattern (deferred-token pitfall: ensure the token cookie is issued) **[unverified]**; token required on login (login-CSRF) and rotated on authentication; logout is POST + CSRF; Origin check on unsafe methods; SameSite=Lax; SSR performs GET only with the `Cookie` header forwarded explicitly, never forwarding `Set-Cookie`.
  - *Cookies/proxy:* `__Host-` prefixed HttpOnly Secure cookie in production (dev profile without prefix); production reverse proxy (not Next rewrites) overwrites `X-Forwarded-*`; backend port reachable only via the proxy; forward-headers strategy configured and tested (spoofed `X-Forwarded-For` must not affect rate limiting); dev uses a Next rewrite for `/api/*` so dev is also single-origin; frontend client must switch to relative `/api/v1` with same-origin credentials. Actuator and Swagger must not be exposed through the proxy in production.
  - *Next.js:* `cacheComponents` is enabled **[fact]**; authenticated data must never be cached or shared between users (`Cache-Control: no-store`; server-only fetch helper using a runtime `BACKEND_INTERNAL_URL`). **[unverified]** caching details.
  - *Tenant isolation:* `activeCompanyId` only in the server session; switch-company validates an ACTIVE membership and rotates the session id; membership and role are re-read from PostgreSQL on **every** request (no cache in the MVP) which gives immediate revocation; modules receive an immutable company context through a `common/security` resolver and never read the session. Every repository method takes `companyId`; cross-tenant access returns 404.
  - *PLATFORM_ADMIN:* two-phase login (no admin authority before TOTP); TOTP RFC 6238, secret encrypted (AES-GCM, key from environment/KMS, key id for rotation), enrollment confirmed by a valid code, hashed one-time recovery codes, replay protection, rate limit, step-up MFA for sensitive actions; cross-tenant access only under `/api/v1/admin/**`, read-only by default, with reason and audit entry; no silent impersonation. E-mail verification and reset tokens: 256-bit random, hashed, single-use, expiring.
  - *Passwords/abuse:* Argon2id with parameters benchmarked on the target host (reviewer floor: OWASP minimum; suggested m=64 MiB, t=3, p=1), min length 12, identical responses/timing for unknown accounts, per-IP and per-account login rate limiting without permanent lockout, all sessions invalidated on password change/reset.
  - *Data model deltas vs spec:* drop `refresh_tokens`; `users` gains `email_verified_at`, MFA fields, failure/lock fields, status; PLATFORM_ADMIN needs a platform-level flag (spec's `company_members.role` is company-scoped); `audit_logs` needs IP, user-agent, request id, outcome; `email_verification_tokens` table. The spec's JWT and `RefreshToken` text is superseded for authentication.
  - *Negative tests required before any business endpoint (security list):* 401 on every non-public route and default-deny for new endpoints; CSRF set (missing, wrong, foreign Origin, login without token, old token after login); session fixation; both timeouts; cross-tenant read/write/list; membership deactivation and role downgrade effective on the next request; forged company id ignored; switch to a non-member company fails; admin without MFA denied; reset/token single-use; enumeration and rate-limit; spoofed forwarded headers ignored; cookie attributes; Swagger/actuator unreachable in prod profile; logout invalidates the server session.
  - *Differences between the two reviews, resolved as recommendations:* (1) absolute-time source: architect proposes a custom `authenticatedAt` attribute, security proposes the native creation time. Prefer the explicit attribute because rotation must provably preserve it; **[unverified]** whether the library keeps creation time on session-id change. (2) Membership cache: security allows a seconds-long cache; architect requires a DB read. ADR-007 says "immediate", so no cache in the MVP. (3) Deleting sessions on role/membership change: architect treats it as optional, security as required. Per-request re-verification is the enforcement; deleting sessions is defence in depth and is **required** for password change/reset. (4) Forward-headers mode: `framework` vs `NATIVE`; choose when the proxy is chosen.
  - *Remaining risks:* all library-behaviour claims above are unproven until TB-002 tests exist; local runs cannot execute the Testcontainers tests (no Docker), so session-table and Flyway checks run only in CI; single-instance rate limiting; the human decisions U-011..U-019 below are open.
  - *Update after TB-002 (2026-11-04):* proven by tests: explicit `authenticatedAt` survives session-id rotation; the deferred-CSRF-token pitfall is handled by a filter that issues the cookie on every response; 12 h absolute and 30 min idle timeouts (idle against the real JDBC store); `changeSessionId` fixation protection; the `SecurityFilterChain` is a catch-all deny-by-default chain. Still unproven: behaviour behind the real reverse proxy (forwarded headers, `__Host-` over HTTPS), Argon2 cost on the target host, tenant isolation (TB-003).
